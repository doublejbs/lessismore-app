## 1. 개요

배낭으로 실제 다녀온 여행의 **운동 기록**(거리·시간·상승고도·경로)을 OS 건강 허브에서 읽어 배낭 상세에 붙인다. UL 백패킹 앱의 맥락에서 **"이 무게로 이만큼 걸었다"** 를 잇는 것이 목적이다 — 배낭 무게(BD-3)와 실제 이동을 한 화면에서 연결한다.

기록은 앱이 직접 측정하지 않는다. 사용자의 시계·폰이 이미 기록해 둔 것을 **읽기 전용**으로 가져온다.

- iOS: **HealthKit**
- Android: **Health Connect**

가민 사용자는 별도 연동이 필요 없다. Garmin Connect가 양 플랫폼의 건강 허브로 단방향 동기화하므로(2020년 이후 워치 → Apple Health, 2025-06부터 Android 14+ → Health Connect), 허브만 읽으면 자동으로 포함된다. **Garmin Connect Developer Program(파트너십·심사 대상)은 쓰지 않는다.**

> **가민은 GPS 경로를 넘기지 않는다 (2026-07-21 실기기 확인).** 거리·상승고도·심박·칼로리 같은 **지표는 오지만 운동 경로(route)는 동기화되지 않는다.** 따라서 가민으로 기록한 여행은 요약·심박은 보여도 **경로 지도가 비어 있다**. 애플 워치·아이폰으로 직접 기록한 운동은 경로가 온다.
> - 이는 우리가 고칠 수 있는 문제가 아니다(Garmin Connect의 동기화 범위).
> - 경로 지도를 이 기능의 핵심 서사로 잡았는데 **주 사용자층(가민 이용자)에게는 동작하지 않을 수 있다** — 요약·심박만으로도 가치가 서도록 화면을 구성한다.

> **선행 조건**: 두 라이브러리 모두 New Architecture를 요구한다(iOS 쪽은 Nitro Modules 기반). SDK 57 + New Arch 마이그레이션이 출시된 뒤에야 배포할 수 있다.

> **폐기 이력**: 과거 `bag.track`(DM-16)이 같은 성격의 데이터를 담으려다 폐기됐다. 사유는 기술적 한계가 아니라 **담을 화면(필드샷)이 기획 단계에서 사라져서**였다. 이번에는 화면(HA-1)을 먼저 확정한 뒤 데이터 모델을 정의한다.

## 2. 화면 및 진입

```
app/(tabs)/bag → bag/[id] (배낭 상세)
  └─ 액션 타일 4번째 `운동 기록` → app/bag/[id]/activity
        └─ BagActivityWrapper → BagActivityView
              ├─ 요약(거리·시간·상승고도·칼로리)
              ├─ 경로 지도 (NaverMapView + 폴리라인)
              └─ 심박·페이스 그래프
```

- 진입 경로: 배낭 상세의 **액션 타일 4번째**. 기존 3개(사용 기록 BD-5 · 메모 BD-6 · 여행지 DST-2)와 같은 2열 그리드에 들어가 2×2가 된다.
- 타일 부제에 요약을 노출한다: 연결된 기록이 있으면 `12.4km · 850m↑`, 없으면 `기록 연결하기`.

## 3. 요구사항

### HA-1 배낭 상세 진입점 `[제안]`

사용자는 배낭 상세에서 그 여행의 운동 기록을 확인할 수 있다.

**수용 기준**

- 액션 타일 4번째로 `운동 기록`을 둔다. 아이콘 + 제목 + 부제(현재값) 구조는 기존 타일과 동일하다.
- 연결된 기록이 있으면 → 부제에 `{거리}km · {상승고도}m↑`
- 연결된 기록이 없으면 → 부제에 `기록 연결하기`
- **권한이 없거나 미지원 플랫폼(웹)이면 타일을 렌더하지 않는다** — 누를 수 없는 진입점을 남기지 않는다.
- **미래 여행에도 타일을 렌더한다**(2026-08-13 사용자 결정 — 이전에는 "기록이 존재할 수 없다"며 숨겼다). 타일이 여행 시점에 따라 생겼다 없어지면 기능의 존재를 학습할 수 없고, 연결 화면의 빈 상태(HA-3)가 "아직 기록이 없다"를 이미 설명한다. 건강 허브가 없는 플랫폼(웹, Android 14 미만, 미지원 기기)에서는 계속 렌더하지 않는다 — 눌러도 갈 곳이 없는 진입점은 두지 않는다.

### HA-2 권한 요청 `[제안]`

사용자는 건강 데이터 접근을 명시적으로 허용한 경우에만 기록을 연결할 수 있다.

**수용 기준**

- **타일을 탭한 시점에** 권한을 요청한다. 앱 시작이나 배낭 상세 진입만으로 요청하지 않는다.
- 요청 범위는 **읽기 전용**이며, HA-4가 실제로 표시하는 항목으로만 한정한다. **표시하지 않는 타입은 요청하지 않는다** — App Store가 문제 삼는 건 데이터의 민감도 자체가 아니라 *기능이 정당화하지 못하는 범위의 요청*이다(예: 한 번에 십수 개 타입 일괄 요청).
- iOS에서 실제로 요청하는 식별자는 다음 6개다.

  | 식별자 | 용도 |
  | --- | --- |
  | `HKWorkoutTypeIdentifier` | 운동 자체 |
  | `HKWorkoutRouteTypeIdentifier` | GPS 경로 — **운동 읽기와 별개의 추가 권한** |
  | `HKQuantityTypeIdentifierDistanceWalkingRunning` | 이동 거리(도보·러닝) |
  | `HKQuantityTypeIdentifierDistanceCycling` | 이동 거리(자전거) — HealthKit이 종목별로 타입을 가른다 |
  | `HKQuantityTypeIdentifierActiveEnergyBurned` | 소모 활동 에너지 |
  | `HKQuantityTypeIdentifierHeartRate` | 심박수 |

  - **누적 상승고도는 요청 대상이 아니다.** HealthKit에 해당 quantity 타입이 없고 워크아웃 **메타데이터**(`HKElevationAscended`)로 딸려오므로, 운동 읽기 권한만으로 얻는다. 고도를 위해 `FlightsClimbed` 같은 대체 타입을 끼워넣지 않는다.
- **iOS는 읽기 권한의 "거부"를 앱에 알려주지 않는다.** Apple이 프라이버시 목적으로 의도적으로 숨기며, API로 알 수 있는 건 *"권한을 물어봐야 하는가"* 뿐이다(`AuthorizationRequestStatus` = `unknown`/`shouldRequest`/`unnecessary`). `requestAuthorization`의 반환값도 "허용됨"이 아니라 "요청 절차가 끝남"을 뜻한다.
  - 따라서 **거부 상태를 분기 조건으로 삼지 않는다.** 권한 요청을 마쳤는데 조회 결과가 비어 있고 **접근 여부를 확인할 수 없으면** `기록이 없거나 접근이 허용되지 않았어요`처럼 두 경우를 함께 안내하고, 설정 앱으로 가는 링크를 제공한다.
  - **단, 운동 읽기 접근이 확인되면 권한 문구를 쓰지 않는다.** 동의를 마친 사용자에게 "접근이 허용되지 않았다"고 안내하는 것은 사실과 다르고 혼란만 준다. 판정 기준은 양 플랫폼 모두 **운동(워크아웃) 읽기 권한 하나**이며, 확인 방법만 다르다.
    - Android(Health Connect): `getGrantedPermissions()`가 허용된 권한 집합을 돌려주므로 운동 세션 권한 보유 여부로 그대로 판정한다.
    - iOS(HealthKit): 허용 여부를 직접 물을 수 없지만, **기간 제한 없이 조회해 운동이 1건이라도 읽히면 운동 읽기 접근이 열려 있음이 증명된다.** 이 프로브는 후보가 0건일 때만 1회 수행하고(평상시 비용 0), 프로브도 0건이면 여전히 판별 불가로 본다. 최신 1건만 받으므로 기간을 좁혀 이득이 없고, 좁히면 오래전 운동만 있는 사용자를 판별 불가로 오분류한다.
    - **이 판정을 다른 용도로 확장하지 않는다.** HealthKit 인가는 타입별이라 프로브가 증명하는 것은 운동 읽기뿐이고 경로·거리·에너지·심박은 여전히 판별 불가다. 따라서 이 값으로 HA-4의 지표·경로 렌더링을 게이팅하면 안 되며, **빈 상태 문구 선택에만 쓴다.** 후보 목록 자체는 운동 읽기만 필요하므로 "운동은 허용, 나머지는 거부"인 사용자에게도 문구는 사실이다.
    - 접근이 확인된 빈 상태에서는 제목·설명에서 권한 언급과 설정 링크를 모두 제거한다(HA-3).
- 어느 경우든 타일 부제는 `기록 연결하기`를 유지한다.
- 권한을 아직 요청하지 않은 상태에서는 **설명 화면을 먼저 보여주고**, 사용자가 명시적으로 누를 때 권한 시트를 띄운다. 이미 허용된 상태면 이 단계를 건너뛴다(매번 거치게 하지 않는다).
- **HealthKit 사용을 앱 UI에서 명확히 드러낸다** (App Store 심사 지침 2.5.1 — HealthKit 관련 거절 중 가장 흔한 사유). 권한 요청 전에 무엇을 왜 읽는지 설명하는 화면을 거치고, `Info.plist`의 `NSHealthShareUsageDescription`에도 같은 목적을 한국어로 적는다.
- **건강 정보를 iCloud에 저장하지 않는다** (5.1.3 명시 금지). 광고·데이터 마이닝에 쓰지 않으며, 건강 허브에 **쓰기(write)를 하지 않는다**(거짓 데이터 기록 금지 조항 회피 겸 기능상 불필요).
- **건강 데이터를 서버(Firestore)로 올리지 않는다.** 원본은 기기에만 두고, 배낭에는 참조와 표시용 요약값만 저장한다(HA-5).

### HA-3 자동 후보 + 사용자 선택 `[제안]`

사용자는 이 배낭 여행에 해당하는 운동을 후보 중에서 고를 수 있다.

**수용 기준**

- 후보는 **여행 기간으로 좁히지 않는다** — 최근 12개월의 운동을 최신순으로 모두 보여주고 선택은 사용자가 한다(2026-08-05 변경).
  - ~~기간: `bag.startDate` 00:00 ~ `bag.endDate` 23:59 (DM-14)~~ — **미적용(2026-08-05)**. 여행 날짜를 대충 잡아 뒀거나 기기 시간대가 어긋나면 정작 그 여행에서 뛴 기록이 목록에서 빠졌다. 좁혀서 얻는 편의보다 빠뜨리는 손해가 컸다.
  - ~~위치: `bag.location` 좌표 기준 **반경 30km** 내에서 시작한 운동~~ — **미적용(2026-07-21)**. HealthKit의 워크아웃 샘플에는 시작 좌표가 없고, GPS는 **별도 권한이 필요한 경로 조회(`getRoute`)로만** 얻을 수 있다. 후보 목록을 만들자고 모든 후보의 경로를 내려받는 것은 비용·권한 범위 모두 과하다.
  - 12개월은 목록 양을 제한하는 창일 뿐 여행과 무관하다. 연결된 운동을 다시 읽을 때(HA-4)는 **여행 기간과 이 창의 합집합**으로 조회해, 12개월보다 오래된 여행의 연결도 깨지지 않는다.
    - 대안이 필요해지면(같은 기간 무관한 운동이 너무 많이 섞이는 경우) 사용자가 고른 뒤 경로를 받아 검증하는 방식이 현실적이다.
- 후보 목록 = 종류·시작 시각·거리·소요 시간. 최신순.
- **자동으로 확정하지 않는다.** 같은 기간에 산책·달리기 등 무관한 기록이 섞일 수 있어, 최종 선택은 사용자가 한다.
- 후보가 0건이면 → 빈 상태를 표시한다. 문구는 **운동 읽기 접근 확인 여부로 갈린다**(HA-2).
  - 접근이 확인된 경우: 제목 `이 기간에 기록된 운동이 없어요` + 다음 행동을 안내하는 설명 한 줄(여행 날짜·건강 앱 기록 확인). **권한 언급과 `설정 열기` 링크를 넣지 않는다.**
  - 확인 불가(권한 요청은 마쳤으나 접근을 증명할 기록이 전혀 없는 경우): 제목 `기록이 없거나 접근이 허용되지 않았어요` + 두 원인을 함께 안내 + 설정 앱 링크.
  - ~~빈 상태에 **전체 목록에서 직접 고르기** 진입점을 제공한다~~ — **미구현(2026-07-28).** 기간 밖 운동을 직접 고르는 경로는 아직 없다. 그래서 접근이 확인된 빈 상태에는 액션이 없다(뒤로 나가는 것뿐) — 진입점을 붙일 때 함께 되살릴 항목이다.
- **복수 선택을 허용한다.** 1박 2일 산행이 날짜별로 나뉘어 기록되는 경우가 흔하므로, 여러 운동을 합산해 하나의 여행 기록으로 표시한다.
- **연결을 확정하면 화면을 닫지 않고 그 자리에서 상세(HA-4)로 전환한다.** 방금 연결한 기록을 바로 확인하는 것이 자연스럽고, 배낭 상세로 되돌린 뒤 다시 들어오게 만들 이유가 없다.
- 연결 해제가 가능해야 한다.

### HA-4 기록 상세 표시 `[제안]`

사용자는 연결된 운동의 요약·경로·추이를 볼 수 있다.

**수용 기준**

- **요약**: 총 거리 · 총 소요 시간 · 누적 상승고도 · 소모 칼로리. 복수 연결 시 합산값이며, 각 운동의 개별 값도 목록으로 보여준다.
- **경로 지도**: 네이버 지도 위에 GPS 폴리라인. 시작/종료 지점을 마커로 표시하고, 경로 전체가 보이도록 카메라를 맞춘다.
  - 실내 운동·서드파티 동기화 등으로 경로가 없으면 지도 대신 **이유를 안내한다**(`이 운동에는 GPS 경로가 없어요. 가민 등 외부 기기가 건강 앱으로 보내는 기록에는 경로가 포함되지 않아요.`). 지도가 말없이 사라지면 고장으로 읽힌다.
- **그래프**: 심박수와 페이스의 시간축 추이. 데이터가 없는 항목은 해당 그래프를 생략한다.
  - **심박 조회는 워크아웃 프리디케이트 + 기간 폴백 2단계로 한다 (iOS 한정).** 워크아웃으로 거르는 쪽이 정확하지만, **가민 등 서드파티가 동기화한 운동은 심박 샘플이 워크아웃 객체에 연결되지 않고 독립 샘플로 들어와** 0건이 된다(2026-07-21 실기기 확인). 그 경우 운동 시간 구간으로 다시 조회한다. Android(Health Connect)에는 워크아웃 프리디케이트 개념 자체가 없어 처음부터 기간 조회 1단계다 — 5절 참고.
  - **페이스는 별도 API가 없어 GPS 경로에서 파생한다.** 순간 페이스는 GPS 잡음에 그대로 노출돼 쓸 수 없으므로 60초 창 평균을 쓰고, 정지 구간(창 이동 10m 미만)과 이상치(60분/km 초과)를 버린다. 경로가 없으면 페이스 그래프도 자연히 생략된다.
  - 복수 연결 시 그래프는 **운동별로 나눠 그린다.** 하나의 시간축에 합치면 날짜 사이 빈 구간(취침)이 그래프 대부분을 차지한다.
- 배낭 무게(BD-3)를 함께 노출해 **"무게 ↔ 이동"** 을 한 화면에서 잇는다.
- 로딩·빈 상태·권한 거부 상태를 각각 처리한다.

### HA-5 저장 범위 `[제안]`

**수용 기준**

- Firestore에는 **참조와 표시용 요약값만** 저장한다(DM-22). 원본 시계열(심박·경로 좌표)은 저장하지 않는다.
- 표시 시점에 기기의 건강 허브에서 다시 읽어 상세를 구성한다. 기기를 바꾸거나 권한을 회수하면 상세는 볼 수 없고, 요약값만 남는다.
- 이유: 건강 데이터의 서버 보관은 심사·프라이버시 부담이 크고, 이 기능에 필요하지도 않다.
- **저장된 워크아웃 id로 못 찾으면 요약값으로 재매칭한다.** HealthKit의 워크아웃 UUID는 영구적이지 않아, 가민 등 서드파티가 기록을 다시 동기화하면 **같은 운동이 새 UUID로 바뀐다**(2026-07-21 실기기 확인 — 저장된 `65B8A7B0-…` 이 기기에서는 `F590207B-…` 로 바뀌어 매칭 0건). id 조회가 비면 여행 기간 내 운동 중 **거리(±50m)와 소요시간(±60초)이 모두 맞는 것**을 찾아 연결을 복구하고, 새 id를 저장해 다음 진입부터는 정상 경로를 탄다.
  - **단건 연결일 때만** 재매칭한다 — 복수 연결은 합산값만 저장해 개별 운동을 식별할 수 없다.
  - **후보가 둘 이상이면 재매칭하지 않는다** — 오매칭(엉뚱한 운동 연결)이 연결 끊김보다 나쁘다.

- 앱 코드는 공용 인터페이스만 참조한다. **웹에서는 타일 자체를 렌더하지 않는다**(HA-1).

### Android(Health Connect)에서 달라지는 것

같은 인터페이스를 채우지만 SDK 구조가 달라 아래 셋은 동작이 다르다. 사용자에게 보이는 차이라 여기 남긴다.

- **지표가 워크아웃에 붙어 오지 않는다.** 거리·상승고도·칼로리가 독립 레코드 타입이라 세션마다 시간 구간 aggregate를 따로 건다. 그래서 **같은 시간대에 다른 운동이 겹쳐 기록돼 있으면 값이 섞인다** — 레코드를 세션에 귀속시키는 API가 없어 피할 수 없다.
- **경로 지도가 사실상 뜨지 않는다.** Health Connect의 경로 읽기는 두 갈래인데, 전체 경로 권한(`READ_EXERCISE_ROUTES`)은 Google Play 별도 심사 대상이고, 레코드 단위(`requestExerciseRoute`)는 **시스템 동의 다이얼로그**를 띄운다. 상세 화면은 경로를 자동으로 불러오므로 후자를 쓰면 열 때마다 다이얼로그가 뜬다 — 그래서 **자동 요청은 하지 않는다.** 경로가 이미 채워져 온 경우에만 표시하고, 없으면 HA-4의 안내로 처리한다.
  - 향후 선택지: ① 명시적 `경로 불러오기` 버튼 뒤에 `requestExerciseRoute`를 붙인다 ② `READ_EXERCISE_ROUTES` 심사를 받는다. **매니페스트에도 경로 권한을 선언하지 않는다** — 코드가 요청하지 않는 권한인데 Google Play는 선언된 권한마다 정당화를 요구해, 소명할 근거 없는 선언은 심사 마찰만 부른다. ①·② 중 하나를 실제로 구현할 때 선언을 함께 되살린다.
- **권한 요청에 MainActivity 초기화가 필요하다.** `react-native-health-connect`는 `MainActivity.onCreate`에서 `HealthConnectPermissionDelegate.setPermissionDelegate(this)`를 호출해야 권한 요청 런처가 초기화된다. 빠지면 권한 요청 시 `UninitializedPropertyAccessException`으로 앱이 죽는다(2026-07-22 에뮬레이터에서 확인). `android/`가 gitignore라 config plugin(`plugins/WithHealthConnectMainActivity.js`)으로 매 prebuild마다 주입한다.
- **`minSdkVersion`을 26으로 올렸다.** `androidx.health.connect:connect-client`가 minSdk 26을 요구해 24로는 매니페스트 머지가 실패한다. `tools:overrideLibrary` 우회는 런타임 크래시 위험이 있어 쓰지 않았다.
- **권한 판정이 iOS보다 정확하다.** 허용된 권한 집합이 돌아와 거부를 확정할 수 있다. 다만 조회(`getGrantedPermissions`)만으로는 "아직 안 물어봄"과 "거부됨"이 갈리지 않아, `Denied`는 `requestPermission()` 결과로만 확정한다.
- **심박 조회가 기간 조회 1단계다.** Health Connect에는 HealthKit의 워크아웃 프리디케이트에 해당하는 개념이 없어, HA-4의 2단계(워크아웃 필터 → 기간 폴백) 중 1단계를 쓸 수 없다. 처음부터 세션 시간 구간으로만 조회하므로 **같은 시간대의 무관한 심박 기록이 섞일 수 있다.**
- **Android 14 미만에서는 타일을 숨긴다.** Health Connect가 OS에 내장되지 않아 별도 앱 설치가 전제인데, 설치를 유도하는 안내까지 붙일 만큼 이 기능의 우선순위가 높지 않다.
- **알려진 한계 — 제공자가 업데이트 필요 상태인 기기.** `isAvailable()`은 동기 메서드라 비동기인 `getSdkStatus()`를 볼 수 없고, 플랫폼·OS 버전만으로 판정한다. 따라서 Health Connect 제공자가 미설치·업데이트 필요 상태여도 **타일은 보이고, 진입한 뒤에야 아무것도 못 하는 상태**가 된다. 화면에는 "기록 없음"과 똑같이 보이므로 구분 단서는 로그(`[HealthConnect] SDK 사용 불가`)뿐이다.

## 7. 미해결 / 판단 필요

- **가민 사용자에게 경로 지도가 뜨지 않는다**(위 개요 참고). 경로가 없을 때의 **안내는 적용했다**(HA-4). 남은 판단: 여행지(DST) 좌표를 지도에 대신 표시해 화면을 채울지 — 경로가 아닌 점 하나가 실제로 가치가 있는지 확신이 없어 보류한다.

- ~~반경 30km 조정~~ → **위치 필터 자체가 미적용**(HA-3 참고). 기간 조건만으로 후보가 과도하게 섞이는지 실사용으로 확인이 필요하다.
- 복수 운동 합산 시 **누적 상승고도**를 단순 합산할지, 이동 구간이 겹치면 보정할지 미정.
- Android 14 미만 기기는 타일이 숨겨진다(결정 내용은 5절). `minSdkVersion`이 26이라 **적지 않은 기기가 여기 걸린다** — 실제 사용자 분포를 보고 재검토한다.
- Android 경로 지도를 살릴지(위 5절의 선택지 ①/②) 미정. iOS도 가민 사용자에겐 경로가 없어, **경로 없이 요약·심박만으로 기능이 서는지**를 먼저 확인하고 판단하는 것이 순서다.
- 심박·페이스 그래프는 **심사 리스크 때문이 아니라 구현량 때문에** 초기 릴리스에서 뺄지 판단이 필요하다(HA-4). 심박은 운동 기록의 표준 구성 요소라 요청 범위로는 정당하다.
