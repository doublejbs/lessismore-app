## 1. 개요

Firebase Auth 기반 인증(Google/Apple/Email), 약관 동의 강제, 정보 탭(계정 관리), 회원 탈퇴를 다룬다.
웹뷰 브릿지는 2026-07-28 폐기됐다(AU-6).

## 2. 화면 및 진입

- 로그인 UI는 별도 라우트가 아니라 **전역 모달**(`LogInView`)이다 — `LogInAlertManager.show()`로 어디서든 호출. 2026-08-11부터 그 모달을 **바텀 시트로 그린다**(AU-1) — 라우트 구조는 바뀌지 않았다.
- `/terms-agreement` — 필수 약관 미동의 로그인 사용자가 강제 리다이렉트되는 화면.
- 정보 탭 → 탈퇴는 `/info/delete`.

```
app/(tabs)/info.tsx → InfoWrapper → InfoScreen
                                     ├─ InfoProfileCardView   (프로필 유리 카드 + 지표 3개, AU-4)
                                     ├─ InfoMenuCardView      (알림 설정 · 서비스 문의 · 처리방침 · 이용약관)
                                     ├─ 로그아웃 카드          (로그인 시에만)
                                     ├─ InfoFooterView        (배지 · VERSION · 사업자 정보 · 탈퇴하기)
                                     └─ InfoNicknameEditView  (닉네임 설정·수정 시트)
```

- `InfoWrapper`가 `InfoStats`(`model/info/`) 도메인 객체를 1회 만들고(앱 공통 3단 래퍼), 화면 포커스마다 `load()`로 지표를 다시 읽는다.
- 하위 화면 3개(`/info/notification` · `/info/policy` · `/info/business`)는 `InfoSubScreenHeaderView` 하나를 공유한다 — iOS는 네이티브 투명 헤더, Android·Web은 커스텀 헤더 행([LiquidGlassNavigation.md](LiquidGlassNavigation.md) LG-1·LG-2 A그룹). 알림 설정도 2026-08-11부터 이 공용 헤더를 쓴다(자체 헤더 행 + 20pt 타이틀 블록 폐기).

### 화면 문법 (as-built, 2026-08-11 — Liquid Depth)

시각만 서술한다. 무엇을 언제 보여주는지는 AU-1~AU-5가 정의한다. 값의 정본은 `.claude/skills/useless-design/`(§11 내 정보 · §12 로그인)이다.

- **정보 탭 지면은 지형 0.8 + 베일**이다(홈과 함께 지형을 쓰는 두 탭 중 하나) — 설정 목록이지만 이 탭에는 프로필이라는 인물 면이 있어, 밋밋한 지면 위에 두면 카드가 붕 뜬다. 콘텐츠는 플로팅 탭바 아래로 흐르고 스크롤 끝에 130을 비운다.
- 위에서 아래로 **정체 → 설정 → 떠남 → 사실**의 네 층이다: 프로필 **유리** 카드(radius 26) → 메뉴 **흰** 카드(radius 22, 헤어라인 4줄) → **가라앉은** 로그아웃 카드(`surfaceQuiet` + 0.5 보더) → 면 없는 푸터. 면의 세기가 그대로 위계다.
- **이 화면의 라임 면은 아바타 하나뿐이다**(48 원 + 이니셜 19/700). `안 쓴 장비` 지표는 면이 아니라 숫자만 라임 계열 잉크(`limeInk`)로 세운다 — 홈 `내 기록`(HM-7)과 같은 처리다.
- 숫자(지표·버전)는 **콘덴스드(Archivo Narrow)**, 한글이 섞인 라벨은 본문 서체다 — 콘덴스드에 한글 글리프가 없다.
- **로그인은 바텀 시트**다: 뒤 화면을 잉크 막(`Liquid.scrim`)으로 덮고, 상단 모서리 32의 유리 시트(`glassFillStrong` + 두꺼운 블러, 상단 0.5px 흰 보더, `sheet` 그림자)를 하단에 붙인다. 시트 안은 워드마크 → 두 줄 약속(22/30) → 보조 한 줄 → 알약 버튼들(h54) → 텍스트 버튼(h48) → 약관 안내다.
- **약관 동의·닉네임 편집도 같은 문법을 쓴다** — 약관 항목은 흰 카드 하나씩(전문은 카드 안 `surfaceSunken` 타일), 닉네임 편집은 로그인과 같은 유리 시트다. 가운데 뜨는 알럿은 이 세대에 없다.
- 하위 화면(알림 설정·약관 및 정책·사업자 정보·회원 탈퇴)은 **지형 없이 지면 + 우상단 라임 글로우**다 — 읽거나 켜고 끄는 화면이라 산세를 깔지 않는다. 목록·표는 전부 흰 카드 하나 안에서 헤어라인으로 갈린다.
- 각진 면은 쓰지 않는다(카드 22, 카드 안 타일 20·18, 시트 상단 32, 칩·버튼은 알약).
- **11.5px 이하 잔글씨는 목업보다 한 단계 진하다**(`inkSubtle`·`#9A9AA2` → `inkTertiary`): 푸터 메타·탈퇴하기·로그인 시트의 약관 안내가 해당한다. 목업 값은 흰 면 위 2.2~2.9:1로 AA(4.5:1)에 못 미치는데, 그 문장들이 "동의로 간주된다"·"탈퇴"처럼 읽히지 않으면 안 되는 내용이다(창고 알림 칩 WH-2-1과 같은 처리). 위계는 색이 아니라 크기·서체·밑줄이 낸다.

## 3. 요구사항

### AU-1 로그인 제공자

**수용 기준**

| 제공자 | iOS | Android | Web |
| --- | --- | --- | --- |
| Google | `GoogleSignin.signIn()` (네이티브 SDK) | 동일 | `signInWithPopup` (동적 import) |
| Apple | `expo-apple-authentication` | **미지원** — 로그인 모달에 버튼 자체가 렌더되지 않음 (`Firebase.logInWithApple`의 방어 에러 메시지는 UI로 도달 불가) | `signInWithPopup` |
| Email | `signInWithEmailAndPassword` | 동일 | 동일 |

- 로그인 시트: 기본 모드(Google/Apple 버튼 + 이메일 로그인 링크) ↔ 이메일 모드(이메일/비밀번호 입력). 시트 밖(지면)을 탭해 닫으면 입력 상태 초기화.
- 이메일 로그인 실패: `이메일 또는 비밀번호가 올바르지 않습니다.`
- 로그인 취소(팝업/시트 닫기)는 조용히 무시한다(에러 UI 없음).
- Auth persistence: 네이티브는 `getReactNativePersistence(AsyncStorage)`, 웹은 `getAuth` 기본값.

**로그인 시트 (as-built, 2026-08-11 — Liquid Depth)**

- **화면 가운데 뜨는 카드가 아니라 하단에서 올라오는 시트다.** 로그인은 앞을 막는 경고가 아니라 "여기서 이어 하자"는 제안이고, 버튼이 엄지 쪽에 있어야 짧다. 전역 모달이라는 구조(`LogInAlertManager` + RN `Modal`)는 그대로다 — 라우트를 만들지 않는다.
- 뒤 화면은 **잉크 막(`Liquid.scrim`)으로만** 덮는다 — 하던 화면이 막 뒤로 계속 보여야 "위에 올라온 시트"로 읽힌다. 공지 시트·닉네임 편집 시트와 같은 막이라 RN `Modal` 기반 시트가 앱 안에서 한 가지 형태가 된다.
- **전환 (as-built 2026-08-11)**: 막·슬라이드는 공용 프리미티브 `components/liquid/LiquidSheetModal.tsx`가 든다 — 진행도 값 하나로 막 페이드와 시트 slide-up을 함께 움직이고(들어올 때 `LiquidMotion.spring`, 나갈 때 200ms timing), 키보드 회피(`avoidKeyboard`)와 막 라벨(`로그인 창 닫기`)도 여기서 나온다. 이식 직후에는 애니메이션이 없어 시트가 툭 나타났다. 닉네임 편집 시트(AU-4)가 같은 프리미티브를 쓴다.
  - **[이력] 2026-08-11 정정**: 목업 §12의 `지형 0.7 + 베일 + blur(2px)`를 그대로 옮겼더니, 불투명 지면이 이전 화면을 통째로 지워 **페이지 이동으로 읽혔다**(비로그인 상태에서 `장비 추가`를 누르면 창고가 사라지고 로그인 화면으로 넘어간 것처럼 보였다). 목업의 지형은 로그인을 독립 화면으로 그린 그 목업의 지면이고, 이 앱에서 로그인은 어느 화면에서든 올라오는 오버레이라 전제가 다르다.
- **제공자 모드에 설명 문구를 두지 않는다** — 워드마크 → 알약 버튼들 → `이메일로 로그인` → 약관 안내가 전부다. 어느 화면에서 올라와도 여기서 할 일은 제공자를 고르는 것 하나이고, 왜 로그인하는지는 눌러서 온 그 화면이 이미 말했다. 버튼은 `Google로 계속하기` · `Apple로 계속하기`(로그인이 곧 가입이라 '계속하기'가 맞다, AU-2), 맨 아래 `계속하면 이용약관 및 개인정보 처리방침에 / 동의하는 것으로 간주합니다`.
  - **약관 안내는 남긴다** — 동의로 간주된다는 고지라 지울 수 없다.
  - 이메일 모드의 `이메일로 로그인` 제목은 유지한다 — 입력 두 칸이 무엇인지 말하는 유일한 라벨이다.
  - **[이력] 2026-08-11까지**: 제목 `가진 것을 알면 / 더 가볍게 떠날 수 있어요` 두 줄 + 보조 `로그인하고 창고와 배낭을 동기화하세요`가 있었다.
  - **[이력] 2026-08-10까지**: 워드마크 + `로그인 후 이용 가능합니다` 한 줄 + `Google로 로그인` / `Apple로 로그인`(둘 다 잉크 면) + 밑줄 `이메일로 로그인`. 약관 안내 문구는 없었다.
- Apple 버튼은 **흰 면 + 1px 보더**다(잉크 면은 Google 하나) — 주 액션 하나 규칙이자 Apple 브랜드 가이드(흰 배경 + 검정 로고)에도 맞는다.
- **요청 중에는 스피너로 갈아 끼우지 않고 버튼을 그대로 둔 채 비활성한다**(알약 앞에 인디케이터 + `accessibilityState.busy`). 예전에는 버튼 묶음 전체가 `LoadingView`로 대체돼 시트 높이가 튀었다.
- **진행 표시는 누른 제공자 버튼에만 붙는다.** `LogInAlertManager`가 진행 중인 제공자를 들고(`getLoadingProvider()`: `google`·`apple`·`email`·`null`), 그 버튼만 인디케이터 + `busy`가 되며 나머지 버튼은 재탭을 막는 비활성만 된다 — 제공자를 구분하지 않는 플래그 하나면 Apple을 눌러도 Google 버튼이 진행 중인 것처럼 읽힌다. 인디케이터 색은 면을 따른다(잉크 면 Google은 흰색, 흰 면 Apple은 잉크). 성공·실패·취소 어느 쪽이든 `finally`에서 해제한다.
- 이메일 모드는 같은 시트 안에서 제목만 `이메일로 로그인`으로 바뀌고 알약 입력 두 칸 + `확인` + `뒤로가기`가 된다. 키보드가 올라오면 시트가 그 위에 붙고(`KeyboardAvoidingView`), 이 모드에서는 시트 하단 여백을 28로 줄인다 — 키보드 위에 붙으므로 홈 인디케이터 자리를 비울 필요가 없다(닉네임 편집 시트와 같은 판단).
- 시트에는 닫기 버튼이 없다 — 시트 밖 영역이 유일한 취소 경로이며, 그 영역에 `로그인 창 닫기` 라벨을 붙여 스크린리더로도 닫을 수 있게 한다.

### AU-3 약관 동의

**수용 기준**

- 항목: 필수 4(이용약관, 개인정보 처리방침, 개인정보 수집·이용, 만 14세 이상) + 선택 2(SMS 수신, 마케팅 활용).
- 동의 완료 판정은 필수 4종 모두 true (DM-2).
- 로그인 상태 + 미동의면 앱 어디서든 `/terms-agreement`로 `replace` 리다이렉트된다(`app/_layout.tsx` 가드).
- 동의 저장 시 6개 필드 + `agreedAt`을 기록하고 `/(tabs)`로 이동한다. 저장 실패 시 알럿 후 화면 유지.
- 제출(시작하기) 버튼은 **필수 4종이 모두 체크된 경우에만 활성화**된다(동의 판정 조건과 동일). 선택 2종은 버튼 활성에 영향을 주지 않는다.

**화면 문법 (as-built, 2026-08-11 — Liquid Depth)**

- 타이틀은 **좌측 정렬 대제목**(`약관 동의` 32/38)이고 그 아래 `필수 항목에 동의하면 시작할 수 있어요` 한 줄이 무엇을 해야 하는지 말한다(신규 카피).
  - **[이력] 2026-08-10까지**: 가운데 정렬 24pt 한 줄. 다른 화면의 화면 대상이 전부 좌측 대제목이라 이 화면만 축이 달랐다.
- 항목 하나가 **흰 카드 하나**다(카드 사이 10). 전문은 카드 안 `surfaceSunken` 타일(radius 20)에서 스크롤되며, 예전의 좌측 30 들여쓰기는 없앴다 — 카드가 이미 구획을 맡는다.
- 체크는 **26 원**이다: 미체크 = 1.5px `inkFaint` 아웃라인, 체크 = 잉크 면 + 라임 체크(패킹 모드 PK-2의 체크 원과 같은 문법). 유니코드 `✓` 텍스트와 각진 사각 체크박스는 폐기했다.
- 라벨 굵기는 체크 여부와 무관하게 고정한다(15/500) — 굵기가 튀면 카드가 줄줄이 놓인 목록의 리듬이 깨진다. `(필수)`는 라벨 안 별도 런(12.5 `inkTertiary`)이라 문자열에 섞이지 않는다.

**화면 문법 (as-built, 2026-08-11 — Liquid Depth)**

- 타이틀 `회원 탈퇴` 32/38 아래에 **경고 면 카드 하나**(`warnBg`, radius 22)만 둔다: 아이콘은 `warnInk`, 문장은 `warnInkStrong`(경고 면 위에서 `warnInk`는 작은 글자 AA에 못 미친다). `⚠️` 이모지는 Ionicons `alert-circle`로 바꿨다 — 이 앱은 이모지를 쓰지 않는다(`📍` 예외 하나).
- 하단 고정 줄은 알약 두 개(`취소` 흰 아웃라인 / `확인` **danger 면**)이고, 지면색 그라디언트로 콘텐츠와 끊는다(불투명 흰 띠 폐기). 처리 중에는 라벨이 `처리중...`이 되고 버튼이 비활성 + `busy`가 된다.
- **`danger` 알약은 앱에서 이 자리 하나뿐이다.** 되돌릴 수 없는 액션에만 쓰며, 로그아웃 같은 되돌릴 수 있는 액션에는 쓰지 않는다(AU-4).
- 안내 문구·알럿 텍스트는 손대지 않았다 — 법적 고지 성격이라 톤(합니다체)을 유지한다.

### AU-6 웹뷰 브릿지 `[폐기]`

**2026-07-28 폐기.** 검색이 네이티브로 전환되면서 웹뷰 진입점이 사라졌고, 라우트 등록만 남은 죽은 코드였다(`/not-login-search`로 이동하는 코드가 앱에 하나도 없었다). `app/not-login-search/`·`components/webview/`·`model/webview/`를 모두 제거했다. 웹(`useless.my`)과의 브릿지 계약(`window.NativeBridge`, `AUTH_TOKENS` 주입 등)도 함께 폐기된다 — 다시 필요해지면 이 절을 새로 쓸 것.

### AU-7 로그인 상태 전파

**수용 기준**

- `onAuthStateChanged` 리스너 + MobX observable로 로그인 상태를 전파하고, 창고/배낭/검색은 reaction으로 자동 갱신한다.

### AU-8 탈퇴 시 데이터 삭제 범위

회원 탈퇴 시 사용자의 실데이터를 안내 문구("모든 데이터가 삭제됩니다")에 맞게 삭제한다.

**수용 기준**

- `deleteUserData(uid)`는 재인증 성공 후 다음을 삭제한다 (`writeBatch`는 500 한도 미만으로 청크 분할):
  1. 사용자 장비 중 카탈로그 장비(`isCustom === false`)의 `gear-rank` count 감소, count ≤ 1이면 문서 삭제 — DM-6 불변 규칙 유지
  2. `users/{uid}.bags`에 기록된 모든 `bag/{bagId}` 문서
  3. `users/{uid}/gears` 서브컬렉션 전체 문서 (Firestore는 부모 문서 삭제 시 서브컬렉션을 자동 삭제하지 않으므로 명시 삭제)
  4. `comment-likes`에서 `userId == uid`인 문서 전체 (`where` 쿼리, 전체 스캔 금지)
  5. `users/{uid}` 문서
- Firestore 삭제가 실패해도 Auth 계정 삭제(`deleteUser`)는 계속 진행한다(현 정책 유지, 콘솔 로그).
- 작성한 댓글(`gear-comments`)은 삭제하지 않는다 — 탈퇴 후에도 닉네임 명의로 남는다 (컬렉션 그룹 인덱스 부재로 클라이언트에서 일괄 조회 불가, 미해결 질문 참조).
- 좋아요 문서 삭제 시 해당 댓글의 `likeCount`는 보정하지 않는다(비정규화 카운트 드리프트 허용, 미해결 질문 참조).
