## 1. 개요

두 종류의 알림을 제공한다.

- **로컬 리마인더** — 기기에서 예약되는 알림. 서버 불필요(`expo-notifications`). 여행 D-1 패킹 알림, 여행 후 사용 여부 기록 유도, **재방문 유도(다음 여행 계획·주말 박지 추천, NT-7~NT-10 `[제안]`)**.
- **원격 푸시** — FCM으로 수신하는 공지. 앱은 권한/토큰 등록·수신만 담당하고, **발송은 Firebase 콘솔에서 수동**으로 한다(백엔드 코드 없음). `@react-native-firebase/messaging`.

> **배포 주의**: 네이티브 모듈(expo-notifications, RNFirebase messaging) 추가라 **OTA 불가** — 새 EAS 빌드(다음 버전, 예: 1.1.7)가 필요하다. iOS는 APNs 인증 키를 Firebase 프로젝트(`lessismore-7e070`)에 등록해야 원격 푸시가 동작한다(사용자 콘솔 작업). Android는 기존 `google-services.json`으로 동작.
>
> **빌드 제약(1.1.7에서 실제로 겪음):**
> - **Android 매니페스트 병합 충돌** — expo-notifications와 `@react-native-firebase/messaging`이 `com.google.firebase.messaging.default_notification_color`를 서로 다른 값(`@color/notification_icon_color` vs `@color/white`)으로 선언해 `:app:processReleaseMainManifest`가 실패한다. config plugin `plugins/WithFirebaseMessagingNotificationColor.js`가 앱 값에 `tools:replace="android:resource"`를 붙여 해소한다(app.json plugins에 등록됨).
> - **iOS Push capability** — `ios.entitlements`에 `aps-environment`(production)를 넣어도, Apple 개발자 포털 App ID에 Push Notifications capability가 켜지고 **프로비저닝 프로파일이 재발급**돼 있어야 빌드가 통과한다. EAS `--non-interactive`는 Apple capability 동기화를 건너뛰므로, 최초 1회는 인증된(`eas build -p ios --profile production`, Apple 로그인) 실행으로 프로파일을 재발급해야 한다.
> - 의존성 추가 후 `package-lock.json`을 반드시 갱신·커밋한다(EAS는 `npm ci`라 lock 불일치 시 Install dependencies 단계에서 실패).

## 2. 구성

- 전역 매니저: `NotificationManager` — `app.getNotificationManager()`로 접근(기존 매니저 패턴). 권한 요청, 로컬 예약/취소, FCM 토큰·수신 처리를 담당.
- 초기화: `app.initialize()`에서 인스턴스화, `app/_layout.tsx`에서 권한 요청 및 리스너 등록.
- **웹은 전 기능 no-op** — 네이티브 모듈은 네이티브에서만 로드(웹 번들 제외, `AnalyticsManager` 패턴과 동일).

## 3. 요구사항

### NT-1 권한 요청 및 초기화

**수용 기준**

- 앱 시작 후(로그인·약관 동의 완료 이후) 알림 권한을 1회 요청한다. iOS/Android 공통 1개 권한으로 로컬·원격 모두 커버.
- `[제안]` **요청 시점 개정(2026-10-08, [Onboarding.md](Onboarding.md) OB-8)**:
  - 시작 시 요청은 **로그인 + 약관 동의 + 첫 여행 가이드 판정(OB-1)이 끝난 뒤** 한다. 이전 코드는 `NotificationManager.initialize()` 안에서 로그인 여부와 무관하게 첫 실행 즉시 요청했다 — 이 줄의 "로그인·약관 동의 완료 이후"와 어긋나 있었고, 신규 사용자는 로그인 화면도 보기 전에 질문을 받았다. 이제 `initialize()`는 리스너·핸들러 등록과 **이미 허용된 경우의** 토픽 구독만 하고, 요청은 `requestPermissionAtLaunch()`(레이아웃이 조건을 확인한 뒤 호출, 세션당 1회)가 맡는다.
  - **이번 세션에 첫 여행 가이드를 띄웠으면 시작 시 요청을 건너뛴다** — 가이드 완료 단계(OB-7)의 `알림 받고 여행 만들기`가 첫 질문이다. 가이드에서 묻지 않고 끝났으면 다음 콜드 스타트에 시작 시 요청이 적용된다.
  - 두 경로 모두 OS 상태가 **미결정(`undetermined`)일 때만** 대화상자를 띄운다. 안드로이드 13+는 한 번 거부해도 `canAskAgain`이 true라 매 실행 다시 떴는데, 이제 결정된 권한은 묻지 않는다 — "1회 요청"을 코드가 지킨다.
  - 비로그인 사용자는 시작 시 요청을 받지 않는다(로그인·동의 후 첫 실행/탭 도착 때 받는다). 그동안 원격 공지(NT-5)는 권한이 없어 표시되지 않는다(수용).
  - `[제안]` 비로그인 첫 실행 가이드(OB-11)를 띄운 세션은 로그인 뒤에도 시작 시 요청을 건너뛰고, 가이드가 로그인 뒤 이어 만들기 직전에 미결정이면 한 번 묻는다(OB-12). 약관 화면을 거쳐 가이드를 다시 연 세션도 같다.
- 권한 거부 시: 로컬 예약·원격 수신을 시도하지 않고 조용히 통과(앱 동작에 영향 없음, 알럿 강제 금지).
- 포그라운드 알림 표시 핸들러를 설정한다(앱이 열려 있어도 배너 표시).
- 알림 예약/전송 관련 실패는 fire-and-forget으로 무시(콘솔 경고만).
- 웹에서는 no-op.

### NT-2 로컬 리마인더 — 여행 D-1 패킹

**수용 기준**

- 배낭 `startDate` **전날 저녁(기본 19:00)**에 로컬 알림을 예약한다. **제목·내용을 분리**해 잠금화면에서 제목(굵게) + 내용으로 표시한다: 제목 `{배낭이름} 여행 하루 전!` / 내용 `패킹을 확인해보세요`.
- 예약 식별자는 배낭 ID 기반으로 결정적으로 만든다(예: `bag-{id}-packing`) — 저장소 없이 취소/재예약 가능.
- 예약 시점이 이미 과거면 예약하지 않는다.
- 알림 탭 시 해당 배낭 상세(`/bag/{id}`)로 이동한다.

### NT-3 로컬 리마인더 — 여행 후 사용 여부 기록

**수용 기준**

- 배낭 `endDate` **다음날 21:00**에 로컬 알림을 예약한다. 제목·내용 분리: 제목 `{배낭이름} 여행 잘 다녀오셨나요?` / 내용 `사용한 장비를 확인해보세요.`.
- 식별자 `bag-{id}-useless`. 과거면 예약 안 함.
- 알림 탭 시 사용 여부 기록 화면(`/useless/{id}`)으로 이동한다.
- `[이력]` 2026-10-10 여행 기록(CM-16) 유도로 개정했다가 같은 날 CM-16 폐기로 원복.

### NT-4 리마인더 스케줄 관리

**수용 기준**

- **배낭 생성/날짜 수정 시**: 해당 배낭의 두 리마인더(NT-2·NT-3)를 기존 식별자로 취소 후 새 날짜로 재예약한다.
- **배낭 삭제 시**: 해당 배낭의 리마인더를 모두 취소한다.
- 예약은 권한이 허용되고 **해당 유형 설정(NT-6)이 켜져 있을 때만** 수행한다.
- 로컬 리마인더는 기기 종속 — 재설치/기기 변경 시 사라질 수 있음(**known issue로 수용**, 서버 동기화 안 함).

### NT-5 원격 푸시 (수동 공지)

**수용 기준**

- 권한 허용 시 FCM 등록 토큰을 획득하고, 전체 공지 수신을 위해 토픽 `all`을 구독한다.
- Firebase 콘솔(Cloud Messaging)에서 토픽 `all` 또는 앱 전체 대상 공지를 발송하면 기기에서 수신·표시된다.
- 포그라운드 수신 시에도 배너로 표시(NT-1 핸들러).
- 푸시 페이로드에 `route`(딥링크 경로)가 있으면 탭 시 해당 경로로 이동, 없으면 앱만 연다.
- 개인 식별 정보는 페이로드·토큰 저장에 넣지 않는다. (수동 발송이라 서버 토큰 저장은 하지 않음 — 토픽 구독으로 타깃.)
- 공지 알림 설정(NT-6)이 꺼져 있으면 토픽 `all`을 구독 해제한다.

### NT-6 사용자별 알림 설정 `[제안]`

사용자는 알림 유형을 개별로 켜고 끌 수 있다.

**수용 기준**

- 정보 탭([Auth.md](Auth.md) AU-4)에 `알림 설정` 진입점을 두고, **4개** 토글을 제공한다(주말 날씨 브리핑 NT-11은 별도 토글 없이 `여행 추천 알림` 토글을 따른다 — 같은 성격의 주 1회 알림이라 토글을 늘리지 않는다):
  `여행 패킹 알림`(NT-2), `사용 여부 기록 알림`(NT-3), `여행 추천 알림`(NT-7·NT-8, `[제안]`), `공지 알림`(NT-5 원격).
- 기본값: 권한 허용 상태에서 모두 **ON**. 기존 사용자의 저장된 설정에 `여행 추천 알림` 키가 없으면 ON으로 본다.
- 토글 OFF 동작:
  - 패킹/사용기록 → 해당 유형의 예약된 로컬 알림을 모두 취소하고 이후 예약하지 않는다. 다시 ON → 현재 배낭들 기준으로 재예약.
  - 여행 추천 → NT-7·NT-8 예약을 모두 취소하고 이후 예약하지 않는다. 다시 ON → NT-9 동기화로 재예약.
  - 공지 → 토픽 `all` 구독 해제. ON → 재구독.
- 설정은 **기기 로컬 저장**(AsyncStorage 등). 로컬 리마인더가 기기 종속이므로 설정도 기기 단위(재설치 시 초기화 — known issue).
- OS 레벨에서 앱 알림이 꺼져 있으면 앱 내 토글과 무관하게 표시되지 않음(별도 처리 없음).

### NT-7 재방문 리마인더 — 다음 여행 계획 `[제안]`

여행을 한 번 다녀온 사용자가 다음 여행을 만들러 돌아오게 한다(2026-10-08 지표: 7일 리텐션 ~2%, 두 번째 여행 15%).

**수용 기준**

- **기준 여행** = 날짜가 유효한 배낭 중 `endDate`가 가장 늦은 배낭. 기준 여행의 `endDate` 날짜 **+10일 19:00(기기 현지 시각)**에 로컬 알림 1건을 예약한다.
  - 기준 여행이 가장 늦게 끝나므로, 예약 시점의 데이터로는 발송 시점에 "다가오는 여행 없음"이 보장된다. 여행이 끝나기 전에 **미리 예약**한다 — 앱을 다시 열지 않는 사용자에게도 도달해야 하기 때문이다.
- 문구: 제목 `다음 백패킹 계획해 볼까요?` / 내용 `지난 여행 장비 그대로 새 여행을 만들 수 있어요`.
- 탭 시 기준 여행을 원본으로 하는 **배낭 복사 폼**(BD-8, `/bag-copy`, `entrySource=notification`)으로 이동한다.
- **여행당 최대 1회** — 발송 키는 `{배낭ID}:{endDate 날짜}`. 이미 발송된 키는 다시 예약하지 않는다. 날짜를 바꾸면 다른 여행으로 본다.
- 새 여행 생성·복사·템플릿 생성·날짜 수정·삭제 시 NT-9 동기화로 취소/재예약된다(기준 여행이 바뀌면 시각도 바뀐다).
- 예약 시각이 이미 지났으면 예약하지 않는다(업데이트 전에 끝난 오래된 여행에 뒤늦게 보내지 않는다).
- 배낭이 하나도 없으면 예약하지 않는다(NT-8이 담당).
- 식별자 `reengage-next-trip`(1건 고정).

### NT-8 재방문 리마인더 — 주말 박지 추천 `[제안]`

가장 많이 쓰이는 신기능인 박지 지도로 돌아오게 한다.

**수용 기준**

- **목요일 19:00(기기 현지 시각)**에 로컬 알림을 예약한다. 문구: 제목 `이번 주말 어디로 갈까요?` / 내용 `가까운 박지를 지도에서 찾아보세요`.
- 탭 시 지도 탭(`/map`)으로 이동한다.
- 후보 목요일은 아래를 모두 만족해야 한다:
  - 그 시각부터 **14일 안에 겹치는 여행이 없다**(진행 중인 여행 포함 — 여행 시작일 ≤ 후보+14일 이고 종료일 끝 ≥ 후보).
  - 직전 발송(이 유형)으로부터 **14일 이상** 지났다 — **14일에 최대 1회**.
  - NT-7 예약 시각과 **3일 이상** 떨어져 있다(재방문 알림이 한 주에 몰리지 않게).
- **앱을 열지 않은 채 3회 연속 발송되면 멈춘다** — 앱을 열 때마다(NT-9) 최대 3건의 체인(각 14일 이상 간격)을 다시 예약하므로, 체인을 다 쓰도록 앱을 열지 않으면 더 이상 오지 않는다. 앱을 열면 체인이 처음부터 다시 잡힌다(14일 간격 제한은 유지).
- 후보 탐색은 최대 26주 앞까지만 본다.
- 식별자 `reengage-weekend-1`~`reengage-weekend-3`.
- **NT-11 브리핑과의 관계(2026-10-10)**: 사용자에게 브리핑 대상 박지(NT-11 선택 규칙 ①~③)가 하나라도 있으면 **NT-8 로컬 알림을 예약하지 않는다** — 같은 목요일 저녁에 일반 문구와 날씨 문구가 둘 다 오지 않게. 대상 박지가 없는 사용자(즐겨찾기·여행지 없음)만 NT-8이 담당한다. 판단은 NT-9 동기화 때 클라이언트가 자기 데이터(즐겨찾기 수·배낭 여행지)로 한다.

### NT-9 재방문 리마인더 스케줄 동기화 `[제안]`

**수용 기준**

- 다음 시점에 동기화(현재 배낭 목록 → 예약 계획 → 기존 `reengage-*` 취소 후 재예약)를 **멱등**하게 수행한다:
  - 앱 시작(초기화 완료 후), 포그라운드 복귀, 로그인·로그아웃 직후.
  - 배낭 생성·복사·템플릿 생성·날짜 수정·삭제 직후(NT-4 트리거와 같은 자리, 짧은 디바운스로 묶음).
  - `여행 추천 알림` 토글 ON.
- 다음 중 하나라도 해당하면 NT-7·NT-8 예약을 모두 취소하고 새로 예약하지 않는다: 설정 OFF, **OS 권한 미허용**(권한 상태만 조회하고 **이 알림 때문에 권한을 요청하지 않는다**), **비로그인**.
- 배낭 목록 조회가 실패하면(오프라인 등) 기존 예약을 건드리지 않고 다음 동기화로 미룬다 — 빈 목록으로 오인해 예약을 지우거나 엉뚱한 알림을 잡지 않는다.
- 계획 계산은 순수 함수(`model/notification/ReengagementPlanner.ts`)로 분리한다 — 입력: 현재 시각·여행 기간·저장 상태, 출력: 예약 시각.
- 상태는 AsyncStorage `notification-reengagement-state`(기기 로컬)에 저장한다: 예약해 둔 NT-7(키·시각)·NT-8(시각 목록), 발송된 NT-7 키 목록(최근 30개), NT-8 마지막 발송 시각. 동기화 때 예약 시각이 현재보다 과거인 항목을 **발송된 것으로 간주**해 옮긴다.
- 개발 빌드(`__DEV__`)에서만 알림 설정 화면에 "10초 뒤 발송" 테스트 버튼을 둔다(프로덕션 번들에는 노출되지 않는다).

### NT-10 알림 열기 지표 `[제안]`

**수용 기준**

- 사용자가 알림(로컬·원격)을 탭해 앱에 진입하면 `notification_open` 이벤트를 `type` 파라미터와 함께 1회 보낸다([Analytics.md](Analytics.md) AN-3 알림 표).
- `type`: `packing`(NT-2) \| `useless`(NT-3) \| `next_trip`(NT-7) \| `weekend_camp`(NT-8) \| `weekend_briefing`(NT-11 원격) \| `notice`(NT-5 원격) \| `unknown`.
- 로컬 알림은 예약 시 `data.type`을 싣는다. 이 기능 이전에 예약된 패킹·사용기록 알림은 식별자 접미사(`-packing`/`-useless`)로 유형을 추정한다. 원격 푸시는 페이로드 `type`이 있으면 쓰고 없으면 `notice`.
- 한 번의 탭이 여러 경로로 들어와도 1회만 보낸다 — 콜드 스타트에서 응답 리스너와 `getLastNotificationResponseAsync`가 같은 응답을, 원격 푸시는 RNFirebase(`onNotificationOpenedApp`/`getInitialNotification`)와 expo 응답 리스너가 함께 받을 수 있다. 3초 안의 두 번째 열기는 유형과 무관하게 보내지 않는다. expo 리스너로 받은 원격 푸시(`trigger.type === 'push'`)에 `data.type`이 없으면 `notice`로 본다.

### NT-11 주말 날씨 브리핑 (원격 푸시, 서버 발송) `[제안]`

여행을 미리 적지 않은 사용자에게도 매주 닿는 알림이다(2026-10-10 사용자 결정, 재방문 1단계). 목요일 저녁, 그 사람이 관심 있는 박지의 **이번 주말 날씨 한 줄**을 보낸다. 날씨는 매주 바뀌어 지난주 알림이 이번 주에 쓸모없어지는 유일한 정보라, 같은 문구가 반복되는 알림과 달리 끄게 만들지 않는다.

**수용 기준**

- **발송**: 웹 레포 `functions/`의 예약 함수 `sendWeekendBriefing`(v2 `onSchedule`, asia-northeast3) — **매주 목요일 18:30 KST**. 운영 변경이 쉽도록 시각·활성 여부는 `config/weekendBriefing`(DM-35)에서 읽고 문서가 없으면 기본값으로 돈다.
- **대상 사용자**: `users/{uid}/push-tokens`(DM-34)에 `briefingEnabled == true`인 토큰이 하나 이상 있는 사용자. 토큰 문서의 `briefingEnabled`는 클라이언트가 `여행 추천 알림` 토글(NT-6)·OS 권한 상태를 미러한 값이다(NT-12).
- **대상 박지 선택(우선순위, 사용자당 1곳)**:
  1. **다가오는 여행의 여행지** — 발송 시각부터 14일 안에 시작하는 배낭 중 가장 빠른 것의 `location.campSpotId`. 이 경우 날씨는 **그 여행 날짜**로, 문구에 D-day를 넣는다.
  2. **즐겨찾기**(DM-21) 중 가장 최근 등록한 박지.
  3. **가장 최근 여행지 박지** — `location.campSpotId`가 있는 배낭 중 `endDate`가 가장 늦은 것.
  4. 셋 다 없으면 **보내지 않는다**(NT-8 로컬 알림이 담당).
  - 선택된 박지가 `camp-spot`에서 비활성·삭제면 다음 순위로 내려간다.
- **날씨**: Open-Meteo 일별 예보(WT-6과 같은 소스·같은 WMO 코드 매핑)를 박지 좌표로 조회한다. 기본은 **이번 토·일**, ①이면 여행 기간(최대 3일만 요약). 조회 실패 시 그 사용자는 건너뛴다(날씨 없는 브리핑은 보내지 않는다 — 날씨가 이 알림의 이유다).
- **문구**(제목/내용, 한국어 — 앱 언어는 알 수 없으므로 토큰 문서의 `locale`을 따르고 없으면 ko):
  - 기본: 제목 `이번 주말 {박지명}` / 내용 `토 {상태} {최저}°~{최고}° · 일 {상태} {최저}°~{최고}°`. 둘 중 하루라도 비·눈·강풍(풍속 최대 ≥ 10m/s)이면 내용 끝에 ` · 바람 주의` 또는 ` · 비 예보`를 한 조각만 덧붙인다(둘 다면 비 우선).
  - ①(여행 예정): 제목 `D-{n} {박지명}` / 내용 `{여행 첫날 요일} {상태} {최저}°~{최고}°`(기간이 2일 이상이면 둘째 날까지 ` · `로 이어 붙인다).
  - 숫자는 반올림 정수. 상태는 WT의 한글 상태(맑음·구름·흐림·비·눈…).
- **딥링크**: 페이로드 `route`는 ①이면 `/bag/{bagId}`, ②③이면 `/camp-site/{spotId}`. `type: weekend_briefing`(NT-10). 페이로드에 개인정보를 넣지 않는다(박지명·날씨·배낭 id뿐).
- **빈도**: 사용자당 **주 1회**, 토큰이 여러 개(여러 기기)면 **모든 토큰에** 보낸다(기기마다 알림 설정이 다를 수 있어 토큰별 `briefingEnabled`를 본다). 같은 주 재실행은 멱등하다 — `weekend-briefing-runs/{weekId}`(DM-35)에 발송한 uid 목록을 적고, 재실행 시 이미 적힌 uid는 건너뛴다.
- **실패 토큰 정리**: FCM이 `UNREGISTERED`/`INVALID_ARGUMENT`로 거절한 토큰 문서는 함수가 삭제한다(죽은 토큰이 쌓이지 않게).
- **상한·비용**: 사용자 수만큼 Open-Meteo 호출이 난다(동일 박지는 1회로 묶는다 — 박지별로 캐시해 중복 조회 제거). 1,000명까지는 단일 실행으로 충분하다. 넘으면 배치로 나눈다(§8).
- **측정**: 서버는 실행 문서에 `targets`·`sent`·`skippedNoSpot`·`skippedNoWeather`·`failed`를 적는다. 앱은 탭 시 `notification_open` `type=weekend_briefing`(NT-10에 값 추가).
- **웹**: 해당 없음(웹은 푸시 토큰이 없다).

### NT-12 푸시 토큰 등록 `[제안]`

서버가 사용자 단위로 푸시를 보내려면 토큰이 서버에 있어야 한다. 지금은 토픽 `all` 구독만 있고 토큰을 저장하지 않는다(NT-5). 이 항목이 그 틈을 메운다.

**수용 기준**

- **등록 시점**: ① 로그인 상태 + OS 알림 권한 허용이 확인된 뒤(NT-1 초기화 끝) ② FCM 토큰 갱신 콜백(`onTokenRefresh`) ③ `여행 추천 알림` 토글 변경(NT-6) ④ 앱 포그라운드 복귀 시 하루 1회 상한으로 재확인. 등록은 멱등(`setDoc` merge)이다.
- **문서**: `users/{uid}/push-tokens/{tokenId}`(DM-34). `tokenId`는 토큰의 SHA-256 앞 32자(토큰 원문을 문서 id로 쓰지 않는다 — URL·로그에 노출되는 자리라서). 필드 `token`·`platform`·`briefingEnabled`·`locale`·`appVersion`·`updatedAt`.
- `briefingEnabled` = `여행 추천 알림` 토글 ON **그리고** OS 권한 허용. 둘 중 하나라도 아니면 `false`로 **갱신**한다(문서를 지우지 않는다 — 다른 유형의 개인 푸시가 생겼을 때 재사용).
- **삭제**: 로그아웃·탈퇴 시 그 기기의 토큰 문서를 지운다(탈퇴는 사용자 문서 트리와 함께 서버 정리 — AU-8). 다른 사용자로 로그인하면 새 uid 아래 다시 등록한다 — 기기 하나의 토큰이 두 uid 아래 남지 않게 **로그아웃 삭제가 먼저**다.
- **비로그인**은 등록하지 않는다(NT-5 토픽 공지만 받는다).
- 토큰은 개인정보 처리방침의 "기기 식별자·푸시 알림" 항목 안이다(AU-4 처리방침, 2026-10 개정분에 이미 명시). 다른 사용자가 읽을 수 없다(규칙: 본인만 읽고 쓴다, DM-34).

## 6. 엣지 케이스

- **권한 거부/미결정**: 예약·구독 skip, 조용히 통과.
- **비로그인**: 로컬 리마인더는 배낭이 있어야 예약되므로 자연히 해당 없음. 원격 공지는 로그인 무관 수신 가능.
- **날짜가 과거인 배낭**: 리마인더 예약 안 함.
- **날짜가 없거나 유효하지 않은 배낭**(빈 문자열 등 → Invalid Date): 리마인더 예약 안 함. Invalid Date(NaN)가 네이티브 trigger로 전달되면 expo-notifications Swift assertion으로 **앱이 크래시**하므로(JS try/catch로 못 잡음), `scheduleLocal`에서 타임스탬프가 유한한 수인지 검사해 차단한다. (2026-07-11 알림 설정 토글 크래시 수정)
- **오프라인/전송 실패**: 무시(fire-and-forget).
- **재방문 리마인더(NT-7·NT-8)**:
  - **시간대**: 예약 시각은 예약 당시 기기 현지 시각으로 계산한 절대 시각이다. 시간대를 옮기면 다음 포그라운드 동기화에서 새 현지 시각으로 다시 잡힌다(그 전에 오는 1건은 옛 시간대 기준일 수 있음 — 수용).
  - **권한 거부**: 상태만 조회하고 요청하지 않는다. 미허용이면 예약을 모두 취소. 나중에 OS 설정에서 허용하고 돌아오면 포그라운드 동기화로 예약된다.
  - **비로그인/로그아웃**: 예약하지 않고, 로그아웃 시 기존 예약을 취소한다(남의 여행 기준 알림이 남지 않게).
  - **여러 기기**: 상태가 기기 로컬이라 각 기기가 따로 예약한다 — 같은 사용자가 두 기기에서 같은 알림을 받을 수 있다(수용). 한 기기에서 새 여행을 만들면 다른 기기는 다음 포그라운드 동기화 때 반영한다.
  - **알림을 껐던 기간**: OS에서 표시가 막혔어도 예약 시각이 지나면 발송된 것으로 간주한다(같은 여행에 다시 보내지 않음).
  - **원본 배낭 삭제 후 탭**: 동기화로 예약이 취소되므로 보통 발생하지 않는다. 다른 기기에서 삭제되고 이 기기가 동기화 전이면 복사 폼이 실패 알럿을 띄운다(수용).

**결정됨**
